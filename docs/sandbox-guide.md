# Codex クラウド・サンドボックスの運用ガイド

作成日: 2026-10-10（日本時間）

## 目的と現在の状態

小さなアプリ、スクリプト、技術調査などを自由に試し、必要になったものだけ育てる場所にする。整備するのは「実験の境界」と「再開するためのメモ」。開始前の手続きや全実験共通の技術選定は増やさない。

ユーザーが承認した方針をもとに、README、AGENTS.md、docs/、experiments/ の入口を用意した。実験のコードはまだない。専門用語の説明は [やさしい解説](plain-language-guide.md)を参照する。

## 推奨する構成

```text
/workspace/
├── sandbox/                        # Git で残す成果
│   ├── README.md                   # 実験一覧とこの場所の目的
│   ├── AGENTS.md                   # Codex が守る短い共通ルール
│   ├── experiments/
│   │   ├── 20261010-example/
│   │   │   ├── README.md           # 目的、状態、実行方法、次の一手
│   │   │   └── ...                 # この実験のコード・依存定義
│   │   └── ...
│   └── docs/                       # 運用ガイド、用語解説、共有する知見
├── scratch/
│   └── sandbox/                    # 一時出力、使い捨ての検証、ダウンロード
└── shared/                         # リポジトリ外の環境内メモなど
```

入口となる README.md、AGENTS.md、experiments/README.md と docs/ の運用文書は用意済み。個別の実験フォルダと scratch/sandbox/ は必要になった時点で作る。空のフォルダは先に量産しない。

`experiments/` は用途別に apps、scripts、notebooks へ細分化しない。同じ実験に複数の形式が混在してよい。日付と短い名前で区別し、作成後の頻繁な移動・改名は避ける。

## 軽い共通ルール

1. 一つの実験は一つのフォルダに閉じる。他の実験を動かす必要がある構成にしない。
2. 各実験に短い README を置く。目的、状態、実行・確認コマンド、必要な設定名、次の一手だけ残す。
3. 依存定義とロックファイルは実験ごとに管理する。最初からルート共通の package.json、Python 環境、モノレポツールを置かない。
4. Python は実験内の .venv、Node.js は実験内の依存ディレクトリを使う。再開時は既存のロックファイルに合わせてインストールする。新規開発で依存を変更したら、その定義とロックファイルも一緒に更新する。
5. .venv、node_modules、ビルド出力、キャッシュ、.env、実データや秘密情報は Git に追加しない。各実験の技術に合わせて .gitignore を用意する。.env.example を使う場合も値はダミーにする。
6. 認証情報は環境設定で管理する。チャット、README、起動ログ、保存スクリプトに秘密の値を残さない。
7. scratch は Git 管理や長期保管を前提にしない。再現に必要なコードと手順は実験フォルダへ移す。scratch を自動削除する仕組みは設けない。
8. 既存の実験やユーザーの変更を勝手に削除・整理しない。終了した実験はまず状態を「完了」「保留」に変える。パスを変えずに残し、削除は明示的に依頼されたときに行う。
9. 共通化は実際に複数の実験で必要になってから検討する。小さいコードの重複は許容する。
10. 各タスクはすでに隔離された環境で動く。既存の checkout を使い、明示的な依頼がない限り Git worktree を追加しない。

## 各実験の README の最小例

```markdown
# 実験名

目的: 何を試し、何が分かれば十分か。
状態: 作業中 / 保留 / 完了

## 実行・確認

作業ディレクトリ、必要なツールのバージョン、依存の導入、起動、
動作確認の具体的なコマンドを書く。アプリなら期待する応答も書く。
必要な環境変数は名前だけ記載し、秘密の値は書かない。

## 結果と次の一手

分かったこと、既知の制限、次に試すことを数行で残す。
```

細かいテスト基盤は一律に強制しない。まずは実行して期待した結果を確かめる。継続して育てる実験には、重要な動作を確認するテストを追加する。

## ルート AGENTS.md の役割

[ルート AGENTS.md](../AGENTS.md)に、この文書の共通ルールを短くまとめている。加えて、作業前にルートと対象実験の README、AGENTS.md、Git の変更状態を確認し、作業対象の実験だけ変更することを指示する。実験固有の制約はその実験の AGENTS.md に置く。

長い設計資料をそのまま AGENTS.md にコピーしない。詳しい背景は README や docs から参照できるようにする。この文書は docs/sandbox-guide.md に置き、環境の起動指示からも参照する。

## 環境の準備方針

今回確認できたツール: Git 2.52.0、Python 3.12.14、uv 0.12.19、Node.js 24.19.0、npm 11.9.0、pnpm 11.19.0。これは現在の環境で確認したバージョンであり、全実験への指定ではない。各実験の要件に合わせて選択・記録する。

最初からデータベース、ブラウザ自動化、GPU 関連ツール、複数のフレームワークを一括導入しない。実験で必要になったものを、その実験の手順として追加する。Docker の実行可否や追加サービスは必要になるまで未検証とする。

環境のインストールスクリプトには安定して必要な準備だけを書く。全実験の依存を毎回インストールする構成にはしない。アプリや DB のプロセスはスナップショットから再開すると考えず、必要になった時点で起動方法と動作確認を start_skill に追記する。

## 当面の運用

- 運用文書と共通ルールを GitHub で管理し、環境の起動指示から参照する。追加インストールは不要。
- 最初の実験を作る依頼が来たら、その内容に合わせて実験フォルダを作り、実験一覧に登録する。
- GitHub に文書を保存することと、クラウド環境の設定を公開することは別の操作。環境設定の反映・公開はユーザーが製品の画面で行う。新規タスクへの復元は今回未検証。

構造を増やす判断基準は「次に開いたときに、目的と実行方法が分かるか」。整理自体を実験開始の障害にしない。
