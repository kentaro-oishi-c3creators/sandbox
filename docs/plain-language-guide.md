# サンドボックス運用案のやさしい解説と用語集

この文書は、チャットで説明した内容を後から参照できるように残したものです。
GitHub やプログラミングを使い始めたばかりの方を想定しています。
具体的な運用ルールは [運用ガイド](sandbox-guide.md)にあります。

## この場所で何をするのか

このサンドボックスは、自由にものづくりできる作業部屋です。
最低限の収納場所とメモのルールを用意し、作ったものが混ざらないようにします。

「実験」は難しい技術研究に限りません。「簡単なホームページを作る」「画像を整理する道具を試す」「気になった技術を触る」など、一つひとつの試みです。

例えば家計簿アプリと画像整理ツールを試すなら、別々のフォルダへ入れます。
後から探しやすく、一方を直したときにもう一方へ影響しにくくするためです。

## 1. クラウド環境、Git、GitHub、リポジトリ

| 言葉 | 噛み砕くと |
| --- | --- |
| クラウド環境 | Codex が作業する、インターネット上のコンピューター |
| Git | ファイルの変更履歴を記録する仕組み |
| GitHub | Git で管理したものをオンラインで保管・共有するサービス |
| リポジトリ | 一つのまとまりとして管理する、ファイルと変更履歴の保管場所 |

今回の `sandbox` は、実験を入れるリポジトリです。
クラウド環境が作業部屋で、GitHub は成果と変更履歴を保管する場所です。

**クラウド環境でファイルを作っただけでは、GitHub に自動保存されません。**
Git で変更を記録し、GitHub に送る操作は別にあります。
「Git で残す成果」は、後から使いたいコードや説明を、変更履歴付きで保管する対象という意味です。

## 2. フォルダ構成とパス

```text
/workspace/
├── sandbox/
│   ├── README.md
│   ├── AGENTS.md
│   ├── experiments/
│   │   ├── 20261010-household-budget/   ← 家計簿の実験例
│   │   └── 20261011-image-organizer/    ← 画像整理の実験例
│   └── docs/
├── scratch/
└── shared/
```

この図は「どこへ何を置くか」の地図です。二つの実験名は説明用の例で、実際にはまだ作っていません。

- `/workspace/`：Codex の作業場所全体。作業部屋に相当します。
- `sandbox/`：今回のリポジトリがある場所。残したい実験を入れる棚です。
- `experiments/`：「実験」の意味。一つの試みごとに専用フォルダを作ります。
- `20261010-household-budget/`：「2026年10月10日に始めた家計簿の実験」という名前の例。日付と短い名前で区別します。
- `docs/`：「文書」の置き場所。この解説や運用ルール、複数の実験で使う知識を残します。
- `scratch/`：途中の出力や一時的な検証を置く場所。残したい成果は実験フォルダへ移します。勝手に自動削除する仕組みは設けません。
- `shared/`：リポジトリ外の環境内メモなどを置ける場所。この名前だから自動で他人に共有されるわけではありません。

末尾の `/` はフォルダを表します。`/workspace/sandbox/` のような「そこまでの住所」が **パス** です。
**ルート** は、対象のまとまりの一番上のフォルダです。リポジトリのルートは今回なら `sandbox/` です。

空の場所を大量に用意せず、実験を始めるときに必要なものだけ作ります。

## 3. README.md は人向けの説明メモ

`README` は「まず読んでください」という名前です。
`.md` は **Markdown** という文章の形式を表します。普通の文章に見出しや箇条書きを付けられます。

各実験には、例えば次の程度のメモを置きます。

> 名前：家計簿アプリ
>
> 目的：毎月の支出を簡単に記録したい
>
> 状態：作業中
>
> 動かし方：ここに操作手順を書く
>
> 現在できること：支出を入力して一覧表示できる
>
> 次にやること：月ごとの合計を出す

**再現** は「後日、同じ手順でまた動かせる」という意味です。
しばらく放置した実験を再開できるよう、動かし方を残します。

**コマンド** は、コンピューターに操作を伝えるための文字列です。
**作業ディレクトリ** は、その操作を実行するフォルダのことです。
同じコマンドでも実行場所によって結果が変わるため、場所と操作をセットで書きます。

自分で全部の手順を理解して書く必要はありません。Codex に「動かし方もメモに残して」と依頼できます。
[実験 README のひな形](experiment-readme-template.md)も用意しています。

## 4. AGENTS.md は Codex 向けの作業ルール

Codex が作業するときに読む注意書きです。例えば次の約束を書きます。

> 新しい実験は専用フォルダへ作る。
>
> 関係のない実験を勝手に変更しない。
>
> 既存のファイルを勝手に削除しない。
>
> 作業後に実行方法と次の一手を残す。

ルートの `AGENTS.md` は、実験全体の共通ルールです。
ある実験だけに特別な事情があれば、その実験フォルダにも `AGENTS.md` を置けます。
毎回同じ注意を伝える手間を減らすための指示書で、操作を物理的に禁止する機能ではありません。

## 5. 依存関係とロックファイル

**依存関係** は、そのアプリや道具を動かすために必要な外部の部品です。
画像の道具なら画像を加工する部品、ホームページなら画面を作る部品を使うことがあります。

| 言葉 | 意味 |
| --- | --- |
| パッケージ | インストールして使う、ひとまとまりの部品 |
| ライブラリ | 他のプログラムから利用する機能の集まり |
| 依存定義 | 必要な部品の一覧を書いたファイル |
| ロックファイル | 実際に使う部品の細かい版まで記録したファイル |
| バージョン | ソフトウェアの版。新旧を区別する番号 |

**インストール** は、必要な道具や部品をコンピューターで使えるように準備する操作です。
ロックファイルがあると、入れ直した際に部品の版が変わって動かなくなる問題を減らせます。
`package.json` は、JavaScript のプロジェクトで必要な部品や実行操作などを記録するファイルの一例です。

「実験ごとに管理する」は、家計簿アプリの部品と画像整理ツールの部品を混ぜないという意味です。
一方で部品を更新しても、もう一方に影響しにくくします。

## 6. Python、Node.js と部品を管理する道具

| 名前 | 役割 |
| --- | --- |
| Python | 自動処理やデータの扱いにもよく使われるプログラミング言語 |
| Node.js | JavaScript という言語をブラウザの外でも動かすための道具 |
| uv | Python の実行環境や部品を管理する道具 |
| npm・pnpm | JavaScript などで使う部品を管理する道具 |

これらを全部使うという方針ではありません。作りたいものに合わせて必要なものを選びます。
環境で確認したバージョン番号を覚える必要もありません。

- `.venv`：Python の実験専用の道具箱。その実験の部品を他と分けて入れます。
- `node_modules`：JavaScript の実験で使う部品が入るフォルダです。

どちらも大量のファイルを含む場合があります。必要な部品の一覧から作り直せるので、通常はフォルダ全体を GitHub へ保管しません。

## 7. .gitignore、.env と秘密情報

**`.gitignore`** は、Git の新しい保管対象に含めないファイルを指定する設定です。
インストールした部品、一時出力、作り直せるファイル、秘密の設定などを対象から外します。
ただし、すでに Git に記録したファイルを後から自動で取り除くものではありません。

**`.env`** は、アプリの設定値をまとめる方法の一つです。
普通の接続先や設定に加えて、秘密にすべき認証情報が入ることもあります。
**環境変数** は、コードに直接書かず、実行時に外から渡す設定です。
**認証情報** は、サービスを使う権限があると示すためのパスワードや鍵などです。

**`.env.example`** は「この名前の設定が必要」と伝えるための見本です。
本物のパスワードを書かず、**ダミー値**（見本用の仮の値）を使います。
この運用では秘密の値はクラウド環境の設定で管理します。

動かし方と必要な設定名は残しますが、秘密の値はチャット、GitHub、説明文、出力記録に残しません。

## 8. 生成物、キャッシュ、共通化

**生成物** は、プログラムや作業によって作られたファイルです。
加工後の画像や、公開用にまとめたホームページのファイルが例です。
**ビルド** は、コードなどを実行・公開しやすい形へ変換してまとめる処理です。
**キャッシュ** は、次の処理を速くするための一時的な保存データです。
**ログ** は、操作や実行中に起きたことの記録です。

作り直せるものは通常 Git に保存しません。ただし「この画像を成果として残したい」なら、残す場所へ移します。

**共通化** は、複数の実験で使う処理を一つにまとめることです。
便利ですが、共通の処理を変えると複数の実験へ影響します。
必要になるまでは似たコードが別々にあってもよいとし、自由に試す段階から複雑な構造を作りません。

**モノレポ** は、複数のプロジェクトを一つのリポジトリで管理する形です。
このサンドボックスも複数の実験を一か所へ入れますが、最初から全実験の実行・依存をまとめる専用ツールは導入しません。

## 9. Git の操作に関する言葉

| 言葉 | 噛み砕くと |
| --- | --- |
| コミット | ファイルの変更を一つの履歴として記録すること |
| ブランチ | 元の履歴から分けた作業の流れ |
| main | 中心となるブランチによく付ける名前 |
| checkout | この運用ガイドでは、実際に作業できる状態で置かれたリポジトリ |
| worktree | 同じリポジトリについて、別の作業場所を追加する仕組み |
| push | 手元のコミットを GitHub などの保存先へ送る操作 |
| clone | GitHub などからリポジトリを手元へ複製する操作 |

最初の確認時、このリポジトリにはまだコミットがありませんでした。
最初の保存後は、その時点から変更履歴が積み重なります。

「既存の checkout を使う」「worktree を増やさない」は、作業場所をむやみに増やさず、今ある場所で実験を分けようという意味です。
Git の操作は Codex に依頼できます。GitHub へ送ってほしい場合は、そのことも伝えてください。

## 10. 環境を引き継ぐための言葉

- **インストールスクリプト**：道具や部品を準備する操作をまとめて書いたもの。
- **start_skill／起動指示**：新しいタスクで Codex が作業を始めるときに読む手順。今回の環境では運用文書とルールを確認する指示です。
- **スナップショット**：準備した環境のファイルなどを、ある時点の状態として保存したもの。
- **ドラフト**：公開前の設定案。
- **常駐サービス**：アプリやデータベースのように、動かしたまま使うプログラム。
- **プロセス**：コンピューター上で実際に動いているプログラム。
- **データベース／DB**：アプリのデータを整理して保存・取り出す仕組み。

スナップショットから戻したときに、アプリが動き続けているとは考えません。必要なアプリは改めて起動します。
今は実験のアプリがないため、常駐サービスは不要です。

**GitHub に文書を保存することと、クラウド環境の設定を公開することは別の操作です。**
起動指示をドラフトへ保存しても、その保存だけで将来の環境へ反映・公開されたことにはなりません。
環境設定で確認・保存し、環境を公開する操作は製品の画面で行います。

## 11. 必要になるまで導入しない道具

- **フレームワーク**：アプリを作るための基本の仕組みや部品がそろった土台。
- **ブラウザ自動化**：プログラムにブラウザを操作させる仕組み。
- **GPU**：大量の計算を得意とする装置。画像処理や AI の計算などで使われます。
- **Docker**：アプリと必要な部品を、まとめた実行環境で動かすための道具。

これらは何かを作る前に全部そろえる必要はありません。実験の目的に必要なものを選びます。
名前を見かけても、準備済み・利用可能・動作確認済みとは限りません。

## 普段の頼み方

例えば、こんな依頼で十分です。

> 家計簿アプリを試しに作りたい。
>
> 専用フォルダに分けて、動かし方と次にやることを残して。
>
> 他の実験には影響させないで。

Codex がフォルダ、必要な部品、説明メモを整えます。
あなたは作りたいものを伝えて、実際の結果を確認すればよく、専門用語を全部覚えてから始める必要はありません。

終わった実験は自動で消さず、まず「完了」「保留」と記録して残します。
この運用で重視するのは、次に開いたときに目的と動かし方が分かることです。
